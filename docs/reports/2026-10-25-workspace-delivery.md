# SmartData 阶段报告：从履约样板走向企业数据工作空间

日期：2026 年 10 月 25 日。

本轮把项目的入口从“处理订单履约异常”扩展为“接入业务数据、检查问题、组织协作”。负责人现在可以先在本机看到有哪些数据、哪里需要核实，再把发现交给运维、分析和决策三类助手及业务人员继续处理。原有履约审批样板保留为专项工具。

当前交付仍是本机运行的产品阶段。它已经有真实的数据读取和工作记录，默认助手按明确规则整理证据与步骤，也可显式接入模型解释。企业登录、持续监测、大规模部署和真实经营效果还需要后续验证；模型协议已通过本机 HTTP 测试服务验收，具体云供应商仍需自己的授权实测。

项目的完整背景、重要决定和长期目标见[项目总纲](../../PROJECT_CHARTER.md)，下一阶段条件见[优化路线图](../roadmap.md)。这份报告只记录本轮新增的使用体验、实现边界和验收依据。

## 为什么要做这次扩展

原有订单履约样板已经检验了一条重要路径：先收集来源证据，识别缺失和冲突，提出规定格式的业务动作，经人工审批后执行，再回到来源系统核实结果。它能回答“这次库存操作是否被批准、执行和验证”，但还不能帮助一家刚接入的企业回答“我的数据在哪里、哪些问题应先处理、谁来接手”。

这次扩展补上后一部分。普适的地方是连接、证据、检查、协作和验证机制；具体字段是否必填、怎样定义收入、哪些库存变化算异常，仍需要业务负责人确认。不能用通用规则替企业决定所有业务含义。

## 这次做成了什么

| 使用者现在可以做的事 | 实际实现 | 判断结果时要注意什么 |
|---|---|---|
| 从空工作区开始 | 提供本机启动、停止脚本，工作区初始没有虚构来源；电商演示由用户明确加载 | 演示记录是合成样本，不能与用户来源混为一份企业结果 |
| 导入或连接来源 | 支持 JSON 文件样本、返回 JSON 的业务 API，以及 PostgreSQL 只读盘点 | JSON 是结构化文本；API 是软件接口。网络来源还需由服务端明确批准目标与凭据用途 |
| 查看资产和字段 | 展示本次观察到的数据资产、字段类型、已读行数、时间和范围 | “已读 1,000 行”不等于全库只有 1,000 行；总量未知时不能推断全量覆盖 |
| 打开问题，核对依据 | 检查缺失、重复、类型混用、时间格式和更新延迟；每项发现附实际观测、规则、建议和证据引用 | 一项发现是待核实的线索；未命中规则也不代表企业整体健康 |
| 让团队分工并与员工交接 | 运维关注更新和异常；分析关注质量；决策汇总高优先问题。任务支持接手、讨论、提交、复核和重新打开 | 默认使用确定性规则，即相同输入按相同检查逻辑得到结果；这不是模型已经理解企业经营 |
| 检查修复是否成立 | 复核需要新的成功盘点、不同内容、更新的采集时间，以及原规则不再触发 | 不稳定采样、总量未知、原字段消失或只有旧证据，都不能证明修复；本轮闭环以完整 JSON 小快照验证 |
| 关闭后继续工作 | 来源、历史发现、任务、讨论和消息保存在本地；重复命令有持久去重记录 | 这是单机保存，尚不能替代企业数据库备份、灾难恢复和多实例运行 |
| 清楚地阅读和操作 | 新工作台提供亚麻朱砂、钛灰古铜、月白水碧三套主题、搜索、证据浮层、学习引导和窄屏布局 | 状态、出处和操作仍靠文字说明；颜色与动画只辅助理解 |

证据指纹使用 SHA-256，它是对输入内容计算的一串固定长度标识，用来核对两次观察是否来自相同内容。指纹不证明业务结论正确，也不能代替原始系统或业务人员复核。

本地原始快照和工作记录放在 `.local/workspace`。文件写入采用原子替换，即新文件完整写好后再一次替换旧文件，降低中途退出造成半份状态的风险。存储目录在支持的系统上限制为当前运行用户访问；无法建立私有权限时拒绝保存。这个保护不等于已经实现加密存储或企业备份。

## 本轮修正了哪些容易造成误解的地方

重新扫描后，旧发现会保留为历史依据，当前页面只统计仍有效的发现，避免把旧问题重复算成当前问题。读取失败会显示失败原因和盘点尝试时间，不能把旧资产说成刚刚观察到的新状态。

任务的“提交处理结果”和“已核验”分开记录。只写一段“已经修好”、引用原始问题，或者在下一次随机样本里没有看到坏记录，都不足以核验成功。当前版本还会拒绝通过删除原问题字段、把该字段全部置空等方式制造表面修复。

凭据只使用服务端环境变量的引用名称，界面不接收或返回密码正文。授权绑定到租户、连接方式、精确端点和数据库分组等用途，防止把某个业务接口的凭据挪作其他用途。配置来源、替换原始快照和撤销来源授权需要本地管理员身份。

本地角色切换是功能演练。一个操作者可以切换不同演示身份，所以它只能证明系统按不同身份检查了交接条件，不能证明真实世界里有两个人审核。企业部署需要接入真实登录服务，再单独检验双人控制。

## 可以怎样验收

安装要求和来源授权的详细配置见[上手指南](../operations/workspace-quickstart.md)。下面先用一个完整的小快照检查产品路径，避免把外部系统权限问题与产品功能问题混在一起。

1. 在 Windows 项目目录执行 `./scripts/start-local.ps1`，打开脚本显示的本地地址。先确认页面是空工作区，没有自动宣称已连接某家企业。
2. 也可以先体验电商示例，查看“演示样本”标记。准备导入自己的数据前，从“数据连接”明确退出演示工作区。该操作只清空纯演示数据，不用于删除用户来源。
3. 以本地管理员添加 JSON 来源，把唯一标识字段设为 `order_id`，填写这份文件的实际采集时间。使用下面两条合成记录：

   ```json
   [
     {"order_id":"A-1","amount":128},
     {"order_id":"A-1","amount":256}
   ]
   ```

4. 查看资产，确认读取了 2 行、2 个字段。打开“业务唯一键出现重复”，核对实际观测、规则、范围和证据指纹。不要只看一个总分判断对错。
5. 组建服务团队，查看重复键任务被分给哪位助手，以及决策助手如何引用高优先任务。选择一个业务演示身份，写下核实说明，接手任务、保存讨论并提交处理结果。
6. 此时直接核验应被拒绝。它还没有新的来源证据，不能用完成说明自证修复。
7. 在本地管理员身份下更新同一来源快照，把第二行的 `order_id` 改为 `A-2`，填写这次新采集的真实时间，再运行盘点。确认旧发现仍可通过任务追溯，但不再计入当前发现。
8. 使用不同于任务完成者的本地审核身份，引用最新盘点进行复核。只有完整观察及原规则不再触发等条件全部满足，任务才应显示已核验。记录这一结论只覆盖这个完整小快照。
9. 导出报告，核对观察范围、检查依据和协作状态。用停止脚本关闭服务后，再启动相同工作区，检查来源、任务、讨论、消息和历史依据是否仍在。
10. 再检查失败路径：服务未启动、来源无权限、读取超时和无效数据都应明确报错，不得自动替换成演示结果。来源断开后，不能继续扫描或用它确认修复。

操作过程中，右下方的工作区版本会变化。版本是这份记录的修订编号；提交命令时带上它，可以防止两个人基于旧状态互相覆盖。接口还使用幂等键，即同一条命令的唯一编号，防止重试变成重复创建或重复处理。

## 距离成熟应用还缺什么

第一项缺口是真实企业接入。需要带着正式接口说明、最小读取权限、脱敏原始响应、分页和限流规则，接入至少一个电商来源和一个库存或订单来源，再验证第二种厂商能否沿用同一套接入方式。现在的有界单次读取不能冒充持续同步、断线续传和全企业覆盖。

第二项是业务含义。需要负责人确认指标公式、字段含义、负责人和适用规则，并用原始账目或来源记录对账。否则“空值”“更新慢”可能只是业务允许的情况，不能直接升级成经营事故。

第三项是生产运行能力。工作区目前是本机文件保存和演示身份；企业登录、细分权限、可靠数据库、备份恢复、客户侧连接、模型数据出口控制及持续监测还要接入并实测。现有 PostgreSQL 结构、长流程工作进程、消息拓扑和部署文件提供方向，但不等于这些生产适配已经完成。

第四项是真实模型与业务效果。可选模型需要证明：只读取获准摘要，引用真实证据，承认未知，超时或无效答复不冒充成功；它不能凭自己的总结把任务改成已核验。然后在影子运行中让专家对照检查。影子运行是“跟随业务给建议，但不改变业务状态”，用来测漏报、误报和建议适用性。

下一门的业务材料应由企业提供：两种真实来源、主要目标与指标定义、历史异常及人工处理结果、数据负责人和独立审核人。双方先约定完成率、处理耗时、错误干预和返工等指标，再从只读、影子运行逐步进入审批执行。只有这段真实运行证据到位，才有依据讨论“成熟可应用”和节省了多少人力。

## 下一阶段优先顺序

先完成本轮运行证据和公开推送记录，再把真实只读来源接入、来源撤销和恢复演练做成可重复的交付包；随后验证模型的证据解释能力与企业业务口径，最后逐项接到已有的审批执行内核。

这样安排的原因很直接：先能看清、查证和协作，再增加自动化。每一阶段都由实际操作与原始证据验收，不用页面完成度、助手数量或一份流畅报告代替业务结果。
