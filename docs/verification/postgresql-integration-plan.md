# PostgreSQL 持久化验收设计

本轮要证明：应用把案件、审批、执行回执和验证结果写进真实数据库后，换一个应用实例
仍能接着工作；两家企业的数据不会混用；并发处理、失败和外部超时不会被误记为成功。
这是一道进入真实试点前的工程验收门，不代表生产部署已经全部具备。

## 使用什么环境

数据库采用 PostgreSQL 18.6 官方镜像，固定版本和镜像指纹。18.6 修复了 18.4 之后的
已公开安全问题，依据见[官方发布说明](https://www.postgresql.org/docs/release/18.6/)。
Testcontainers 2.0.5 负责为测试启动临时的真实数据库，结束后清理；它不会把数据库
行为换成内存模拟。Java 依赖沿用 Spring Boot 4.1.1 管理的 jOOQ 3.21.7 和 Flyway 12.4.0，
保留本项目已核验的 Jackson、Tomcat 安全补丁。

迁移账号和应用账号分开。迁移账号建表、升级并建立测试租户；应用账号没有超级用户、
绕过行权限或表所有者权限，只获得仓储需要的表权限。测试不通过应用账号建表。

本机已检查 Windows 官方安装路径、服务、登记、命名管道以及 WSL Ubuntu 中的 Docker
命令与引擎连接，没有发现可用 Docker。默认测试和 GitHub Ubuntu 作业仍必须实际启动容器；
容器不可用必须失败，不能自动跳过或改用 H2。

为提前发现真实 SQL 问题，本地另使用 PostgreSQL 官网指向的 EnterpriseDB 18.6-5
便携发行包。下载后逐字节核对官方 SHA-256，再在本项目 `.local` 测试目录建立独立数据库，
只监听本机。此通道必须显式传入本地元数据路径；CI 明确禁止使用它，也分别记录环境来源。
进程中断测试先核对实际数据目录、服务进程、启动时间及数据库集群编号，才允许停止这个
测试实例，不能停止任意给定地址的数据库。两种通道都打开真实磁盘同步，不以关闭刷盘换取通过。

## 哪些结果必须成立

| 检查 | 具体做法 | 通过条件 |
|---|---|---|
| 新装与升级 | 空库迁移；另从 V1 建立旧 UUID 记录后升级 V2 | 迁移校验通过，旧行与 ID 保留；旧版没有保存的案件—主张关系必须显式导入，不能猜；新业务字符串 ID 原样读回 |
| 账号边界 | 尝试以迁移账号、表所有者及所有者成员启动仓储，检查可切换角色、建库建角色和整表清空权限 | 不安全账号被拒绝；正常最小权限应用账号通过；临时同名表不能替换受保护表 |
| 企业隔离 | 同一业务 ID 分别写入两家企业；直接用应用账号查询、插入及修改另一家的记录 | 本企业正常；跨企业读不到、改不了，也不能伪造归属 |
| 连接复用 | 在一笔事务设置企业范围，提交或回滚后复用同一连接 | 范围不会带入下一笔事务；未设置范围时看不到业务行 |
| 并发版本保护 | 两个仓储实例同时按同一个旧版本更新同一案件 | 只有一个成功，另一个得到版本冲突，不覆盖已提交结果 |
| 动作真实意图 | 让两次动作插入同时进入数据库，故意使用相同指纹但不同输入 | 只能保存一个真实意图，另一笔明确冲突；指纹相同不能代替输入相同 |
| 原子回滚 | 在案件、子记录及待发事件写入中途注入异常 | 这组修改共同回滚，不留下半条业务记录或孤立事件 |
| 事务范围 | 在只读事务中写入、在已绑定企业的事务中切换企业 | 明确拒绝，不静默扩大权限 |
| 历史事实 | 更正同一主张，修改证据或已保存的执行尝试；重新读取旧案件版本 | 更正生成新修订，旧证据和旧回执不能覆盖；外部调用不占用数据库事务 |
| 精度与标识 | 比较微秒精度时间、JSON 数字及置信分数；尝试业务 ID 与内部 UUID 别名碰撞 | 合理重放保持幂等，低于可信阈值的分数不能被四舍五入抬高，别名不能覆盖旧行 |
| 命令结果账本 | 命令、业务状态、审计和事件共同提交或回滚，比较带版本的请求指纹 | 同一请求可读回，旧版与新版指纹不能混同；这一底层接口不等于生产 HTTP 去重已接通 |
| 可恢复记录 | 重建连接池和仓储，再重启真实数据库进程读取 | 已提交的案件、审批和结果保留，未提交的内容不出现 |
| 审批后执行 | 保存待审批申请，重建应用对象后审批并执行、独立验证 | 未审批不能执行；成功必须有回执和独立来源证据 |
| 模糊超时恢复 | 外部系统已受理但返回未知；换应用实例后重放与对账 | 保留未知状态，不再次调用写操作；独立观测后才判定结果 |
| 执行中断 | 只保存执行租约，模拟没有回执的应用中断，等租约过期再恢复 | 不盲目重试写操作，进入待对账状态 |
| 待发事件 | 并发领取、租约过期、旧令牌确认以及跨企业领取 | 一个有效领取者；旧令牌无效；另一家企业无法取走事件 |

“行级安全（RLS）”是数据库自身按企业范围限制每一行的机制。“版本保护（CAS）”是
提交时确认记录仍是自己读取的那个版本。“事务”让一组数据库修改共同成功或共同回滚。
“Outbox”是在同一事务内保存的待发事件清单；它能防止业务已经提交却没有事件记录，
本轮没有宣称跨数据库与消息系统的端到端恰好一次投递。

## 怎样留下验收证据

真实数据库测试独立于普通单元测试，使用单独的 `integrationTest` 任务和 CI 作业。
CI 必须实际执行测试、检查结果非空且无失败或跳过，确认报告来自 Testcontainers 而非
本地便携通道，并保留 JUnit XML 与测试报告。
镜像指纹、依赖锁、新增文件指纹及构建后的依赖清单随源码维护。

本轮阶段报告区分：普通测试、本地真实 PostgreSQL、远程真实容器，以及尚未验证的生产能力。
实际结果已记录在[业务与数据库验收](2026-10-25-business-postgresql-release.md)：
本地 PostgreSQL 和首轮云端 Testcontainers 均实际执行 20 项，失败、错误和跳过均为 0。
这里的审批和业务系统仍使用确定性仿真器；真实数据库通过不能替代真实企业连接器、
企业身份、OPA/OpenFGA 权限适配、备份恢复或容量验收。生产启动门继续保持关闭。
