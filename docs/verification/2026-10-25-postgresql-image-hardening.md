# PostgreSQL 交付镜像修复与验收

本轮修正演示部署遗留的 PostgreSQL 18.4 镜像。核验发现，升级数据库版本还不够：
官方候选镜像里两个附带组件仍有已知问题。因此保留固定的官方基础镜像，重建切换
普通账号的小工具 gosu，并更新压缩解码库 Brotli，再实际检查运行结果。

## 为什么不能只改版本号

官方 Docker Hub 与 Registry 对 `18.6-alpine3.22` 均返回 404。维护者当前提供
Alpine 3.23 和 3.24，默认线为 3.24，见[固定源码版本的构建定义](https://github.com/docker-library/postgres/tree/e00e1bd34ec5c8a8e7ad89b273b3d42efaf6d5bc/18/alpine3.24)。
采用 18.6-Alpine 3.24，保留 PostgreSQL 18 与原有数据目录挂载。

对未修改的官方镜像做实际远程扫描，发现 26 个 HIGH 和 1 个 CRITICAL：一个来自
Brotli 1.2.0-r1，其余来自 gosu 内嵌的 Go 1.24.6 标准库。HIGH/CRITICAL 分别表示
高危和严重级别。没有因镜像来自官方就把它视作已经安全验收。

## 做了什么修改

- 固定官方 PostgreSQL 和 Go 编译器镜像的版本及 SHA-256 文件指纹；Docker Hub、
  Registry 响应头和独立计算的镜像清单指纹逐项一致。
- gosu 保留 1.19 原始源码，固定提交和源码压缩包指纹，使用 Go 1.27.3 重建。
  模块依赖依据上游校验清单 `go.sum` 核对，保留编译后的函数名称等检查线索，
  即“二进制符号”，方便后续检查漏洞。
- Brotli 更新到 1.2.1-r0，分别固定 amd64/arm64 安装包的版本与完整指纹。
  构建中仍须通过 Alpine 的安装包签名检查，没有允许不可信签名。
- 保留 gosu、Go、模块依赖和 Brotli 的许可证原文与重建说明。
- 数据库容器默认以普通 postgres 账号运行。Compose 始终按固定配方构建，测试禁止
  从外部拉取一个同名镜像；测试还要核对本次构建的实际镜像编号。

完整来源、文件指纹、许可证和架构范围保存在[镜像清单](postgresql-images.json)。
派生镜像目前由源码配方构建，没有宣称已向公共镜像仓库发布其最终指纹。

## 已实际通过的节点检查

检查在用户授权的 Linux amd64 节点执行。构建限制 2 核、4 GiB，扫描与临时数据库
分别限制 2 核、2 GiB，没有使用 GPU 计算，也没有停止既有工作负载。

最终构建使用的 Dockerfile 指纹为
`85c4cc6f2ee1677d69f392a59549cb81ef027510df2a0c85bacbc54180f97ba8`，
节点实际镜像编号为
`sha256:1b064643612729e7604165f470518b16331f274cb9986f8d9045738e4de33bb6`。

漏洞扫描工具 Trivy 0.74.0 对这个实际交付镜像扫描，包含尚无修复版本的问题，**HIGH/CRITICAL 为 0**。
没有增加漏洞忽略或“不可达”例外。数据库更新时间与原先 27 项扫描相同，均为
2026-10-25 12:57:48 UTC；修复前后比较没有通过更换扫描范围获得零项。
本次扫描报告指纹为
`bfacc7a95e16c5fc05fce0ee3c6ef8ec51b64cf9f5db3a7021a180f70b1498e4`。

另实际启动了独立、没有外部网络的新数据库容器，验证：默认账号不是管理员，
gosu 1.19 确实由 Go 1.27.3 编译且能正确切换账号，Brotli 版本正确，PostgreSQL
实际为 18.6，磁盘同步与完整页写入开启。写入一条合成记录后重启容器，记录仍可读回。
这次容器和新建匿名卷已按唯一归属标识清理，没有操作用户已有数据库卷。

官方 Docker Compose v5.6.1 独立工具也经过官方制品指纹与校验清单双重核对，
实际执行完整演示配置检查通过；这次检查没有启动或升级本机服务。
