# 0006：把履约执行内核的记录可靠地存进 PostgreSQL

状态：仓储实现完成，已在本地真实 PostgreSQL 18.6 通过 20 项集成测试，全部
无失败、无跳过；容器环境仍需由 CI 实际执行验收。生产启动门继续关闭。

## 这次解决什么

此前履约案件、审批动作和回执放在内存中，进程停止后会丢失。新增 PostgreSQL
仓储后，这些记录按业务对象分别保存，支持进程重启后继续核对；不会把整家企业
打包成一个 JSON 文件存进数据库。通用工作区的本地文件存储仍是另一个能力，
本次没有悄悄把它切到数据库。

案件、建议、动作、回执、验证、记忆和审计各有仓储。主张、证据、知识缺口、
案例与证据之间的关系、每次执行尝试、独立验证断言和记忆来源都有独立关系行。
动作参数与少量审计说明保留有界 JSON；原始附件依然不进入这些业务状态表。

企业部署使用独立的基座元数据数据库；不能把这些权威记录表直接建到客户 ERP、
WMS 或其他来源系统的数据库中。读取来源和保存基座记录使用不同连接、账号与权限。

## 保留旧表与旧编号

原 V1 SQL 使用 UUID，即数据库常见的固定格式编号。领域接口也允许类似
`case-order-001` 的业务编号，不能一律强制转换为 UUID。本次 V2 是扩展迁移：
保留原 UUID 主键和外键，增量增加 `business_id` 及租户内唯一约束。已有 UUID
回填为同样的业务编号；新业务编号与数据库内部 UUID 分开保存，读回时不改变
用户看到的编号。旧写入端没提供业务编号时，由触发器自动填入原 UUID 文本。
若另一个业务编号恰好与已分配的内部 UUID 撞号，会明确拒绝；不能把原业务编号
改成新编号，也不能以“编号相同”为理由合并或覆盖记录。不同租户仍相互独立。

V1 没有保存“案件属于哪些主张”的关联，所以历史行不能按订单号猜配。原记录
全部保留，旧案件默认标记上下文待迁移；必须显式提交原案件的主张与证据关联后，
才允许把它交给内核读取。无歧义的旧证据数组、验证断言和来源关系会实际回填。

V1 的置信度只保留四位小数，可能把 0.94999 四舍五入到 0.9500，错误跨过内核
0.95 的信任门槛。V2 新增精确分数字段，保留原列兼容旧端，运行时读取精确字段。
历史已经被四舍五入的值不能靠回填还原原始精度；新适配器只保证新输入的分数
不再丢失这部分精度。旧案件重新启用前仍需核对其原始来源和上下文。
证据本体不可覆写。主张使用独立、不可变的修订记录；案件的每个版本引用具体
修订，而不是永远指向会变化的“当前主张”。同一业务主张更正内容、状态或时间时，
数据库触发器追加修订，保留旧证据关系，更新当前投影；旧写入端也遵循这一规则。
因此后来更正主张，不会改掉旧建议、审批和历史案件版本当时所依据的事实。

## 一次提交到底包含什么

`RepositoryUnitOfWork` 是“把一组数据库修改一起提交或一起撤销”的接口。相同租户
的嵌套操作共用连接；不能在里面换租户，也不能把只读事务升级为写事务。即使
外层捕获了内层失败，这次写入仍会整体回滚。

案件、动作和记忆的更新要求带旧 `stateVersion`，成功后只递增一个版本。这就是
CAS：只有数据库里仍是预期的旧版本，修改才生效。两个进程争取执行同一动作时，
数据库负责选出一个成功者。幂等键另有租户内唯一约束，避免重复创建业务动作。

模型生成建议、外部策略判断、执行来源系统以及独立验证，都在数据库事务外。
执行前先持久记录执行占用状态；外部回执回来后，再用新的短事务保存回执、动作、
案件、审计和待发事件。进程若在外部执行后中断，没有回执时必须等执行租约到期
并转入未知结果对账，不能再次写来源系统试运气。

审计追加记录与 outbox 同事务提交。outbox 是“已经记录、等待发送”的消息清单；
发布者先领取有限时间的占用凭证，在事务外发送，收到消息系统确认后再登记已发。
凭证过期或被别的发布者接管，旧凭证不能确认成功。它支持至少一次投递，不承诺
数据库与消息系统之间永久只有一次投递；消费者仍须按事件 ID 去重。

命令登记簿保存请求摘要的版本和摘要值，旧的 64 位十六进制摘要与 HTTP 新的
`v2:` 摘要分别识别；即使摘要字符相同，两个版本也不能互相冒用。返回结果只
保存资源类型、编号和版本，不保存可绕过新权限检查的完整 HTTP 回复。登记簿
目前是独立存储接口，生产 HTTP 幂等网关仍未装配；不能把这项能力写成线上命令
已经全都获得持久幂等保证，更不能把外部调用包进一个长数据库事务里来实现它。

## 租户和账号边界

每个读写事务用参数化 `set_config(..., true)` 设置当前租户，只在该事务生效，
不把租户字符串拼成 SQL。所有新增表都启用并强制 RLS，即由数据库逐行限制租户。
迁移账号与运行账号分开：受控迁移账号需要读取被强制隔离保护的旧数据，运行账号
则必须没有超级用户、绕过 RLS、表所有者或所有者角色继承、公开 schema 建表权限。
适配器连接时会检查这些条件，不能以管理员连接“先跑起来”。
运行账号也不能直接或通过可切换角色拥有 `TRUNCATE`，即一条命令清空整张表的
权限：PostgreSQL 的逐行隔离不保护这类操作。启动检查会实际拒绝这一配置。
部署授权只给数据库连接、业务 schema 的使用权限，以及各表所需的 `SELECT /
INSERT / UPDATE / DELETE`；不要使用 `GRANT ALL`。建表、改表、清表及角色管理
留给独立迁移账号，不向应用账号开放。
连接的表查找顺序固定为系统目录、公开业务表、临时表；临时同名表不能遮蔽真正
启用租户隔离的业务表。租户设置随事务结束清除，复用连接时不能继承上一租户。

SQL 由 jOOQ（构造和执行数据库语句的 Java 工具）通过 JDBC（Java 连接数据库的
标准接口）参数化执行；jOOQ 的 SQL 和异常正文日志关闭。当前兼容接口
的整批列表超过 1,000 条会明确拒绝，不悄悄截断；数据库仓储另提供按业务编号的
游标分页。现阶段尚未据此宣称达到千万记录容量或既定延迟目标。
数据库时间精度统一到微秒，再做重复提交比较；同一输入中的纳秒部分被数据库
规范化后，不应使重试误报为新请求。回执的外部请求编号和原创建时间不可替换；
源系统时间保留在执行尝试和证据里，内核记录更新时间采用内核时钟。
历史执行尝试只能追加，不能删去或改写已有轨迹；应用检查旧记录前缀，数据库也
拒绝修改和删除尝试行。回执只能引用同一动作的验证，执行验证与补偿验证分别
绑定，不能借用另一动作的成功结果。

## 怎样启用与验收

存储能力要求显式选择 `postgres` profile，并设置
`smartdata.persistence.enabled=true`。它只提供仓储和数据库事务，不提供演示
连接器、宽松策略、企业登录替代品或生产执行内核。生产所需的其他组件缺失时，
启动继续失败；不能因为数据已入库就放开业务写入。
`local` 与 `postgres` 两个 profile 不允许混用，即使没打开存储启用开关也会明确
报错，防止界面仍用演示内核却让操作者误以为正在使用生产数据库。

真实集成验收使用 PostgreSQL 18.6：V1→V2 保留、普通账号及直接 SQL 的租户隔离、
连接复用、并发 CAS、跨聚合回滚、进程重启、模糊外部结果恢复、outbox 租约与旧凭证
拒绝都须实际测试。完整测试计划和结果另记验证报告；H2 或模拟数据库不能代替。
本地这 20 项已实际验证上述边界，包括强制中止自有数据库进程后，从写前日志
（WAL，用于崩溃后恢复已提交修改的记录）恢复。Windows 本地没有 Docker，故本地
结果明确使用经官方哈希核验的独立 PostgreSQL 实例；CI 仍强制使用固定镜像的
Testcontainers（在真实容器中自动启动测试数据库的工具），不会自动跳过或降级。
