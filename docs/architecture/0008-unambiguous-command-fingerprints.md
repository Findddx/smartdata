# 0008：防重复标识必须保留请求的结构

日期：2026-10-25。状态：已实现并通过普通与真实数据库回归，
[实际验收结果另记](../verification/2026-10-25-business-postgresql-release.md)。

## 为什么要改

防重复编号相同，还需要核对请求内容是否相同。旧实现曾把字段和对象的文字表示
用分隔符拼接，再计算摘要。若字段本身包含分隔符，或者两个对象的文字表示相同，
不同请求可能被误认成同一请求。这不是摘要算法被破解，而是摘要之前已经丢失
了字段边界与类型。

## 两处边界各自处理

HTTP 命令使用 `v2:` 前缀，先把操作、身份、角色、资源和请求正文序列化为结构化
JSON，再计算 SHA-256 摘要。对象属性和映射键排序；列表顺序、空值、文本、数字、
对象与列表的结构保留。身份也以对象保存，不能事先把身份和角色拼成一段文字。
这是当前请求模型的确定性序列化，不声称实现了完整 RFC 8785 标准。

执行内核对业务动作另有版本化摘要，以长度和类型标记保留字段边界，并在重放时
核对已经保存的动作语义，包括输入、证据、申请人、案件及版本。不能仅因为一个
旧摘要相同就绕过这些核对。用于生成既有业务编号的算法保持原样，避免编号漂移。

内存中的租户与命令编号使用二元组作为键，不使用可以与字段内容混淆的字符串
拼接。数据库使用独立列和联合唯一约束表达同一边界。

数据库命令账本另存摘要版本，旧 64 位十六进制摘要与 HTTP v2 摘要可以分别读回；
相同摘要文字却不同版本仍视为冲突。账本是底层组件，当前尚未装配成生产 HTTP
防重复网关；不能据此宣称所有网络命令已经获得数据库级重放保护。

## 旧数据的限制

本地工作区旧日志只保存摘要，没有完整原请求，无法安全恢复已经丢失的信息。
升级仍能读取来源、发现、任务和历史；旧防重复编号重放若与新摘要不一致，返回
冲突，不再次执行。操作者应先核对原操作的当前状态；不能自动换一个新编号重试。
这是一项明确的兼容性限制，不能通过接受有歧义的旧摘要来掩盖。

验收覆盖字段分隔符转移、空值与文字、数字与文字、对象与文字、映射键顺序、列表
顺序及租户/编号组合碰撞；业务动作另检查旧摘要下的实际语义和申请人。
