# 数据分层与血缘：一张图应该告诉你什么

分层回答“这是什么阶段的数据”，血缘回答“这个结果从哪里来、怎样得到”。两者一起
才能帮助人判断结果能否用于工作；层级高不代表更真实，图画得漂亮也不代表依据充分。

## 用电商数据说明四层

| 层级 | 保存什么 | 例子 | 最需要核对什么 |
|---|---|---|---|
| L0 原始层 | 来源记录与实际观察到的结构 | 订单表、字段、来源时间 | 是否完整、过期、缺失、重复；权限是否允许读取 |
| L1 实体层 | 按明确规则整理出的业务对象 | 客户、客户特征、商品 | 身份怎样对应，哪些记录合并，未知身份怎样处理 |
| L2 分析层 | 按确认口径计算的指标或分析 | 每日订单额、活跃客户数 | 时区、退款、去重、输入范围、定义版本，能否重新算出相同结果 |
| L3 决策层 | 基于结果提出的业务计划 | 复核异常订单、联系负责人 | 依据、风险、权限、谁批准、怎样确认效果；计划不等于已经执行 |

路径不必逐层经过。本轮实验中，客户汇总是一条支路；28 天指标直接汇总原始
订单，计划再引用日指标。不能为了排出四列，就把实际不存在的“客户实体→日指标”
加工关系画出来。

例如“客户画像”不能只靠给几个字段起个名字就算完成。必须说明使用了哪些来源、
按什么身份规则聚合、排除了什么，以及更新与授权如何处理。不确定是否同一客户时
保留未知，不能为了图连得完整而猜配。

## 节点与线的视觉约定

颜色表示层级：蓝色是原始表，朱红表示业务实体，低饱和绿表示分析，古铜表示决策。
图标与形状进一步区分来源、表、字段、实体、指标与计划。风险另用文字和标记，
不能把同一个红色既解释为“一级实体”又解释为“危险”。

箭头表示依赖方向。实线表示已有观察依据；虚线表示有人登记了来源关系；点线
表示未来计划。每一条线都应能点开解释依据。若只有表级来源，就明确写表级；
不知道字段怎样变换，不应补画一条确定的字段关系。

规模变大时，不能先把十几万个节点传到浏览器再说“已经折叠”。服务端需要显示
预算和覆盖数量，字段按表分批查看；省略依赖时明确提示，不能拿局部视图做完整
影响判断。这是性能设计，也是防止人被图误导的业务要求。

权限、敏感程度和新鲜度各自是另一维信息。没有敏感分类时写“未知”，不能因为
字段名像普通业务字段就替企业宣布它可公开；移出本轮工作范围也不等于撤销权限。

## 登记定义与实际生成要分开

登记“销售额来自订单”只是定义，并没有算出销售额。因此产品中的声明节点会
明确写“尚未生成”，指标确认也只确认含义。真正生成结果后，还应有输入、规则、
运行时间、版本、输出记录数和校验凭据。

本轮在用户指定的 GPU 节点开展合成实验：以250000条订单与10000名合成客户为输入，
分别生成客户汇总和28天指标，计划再引用日指标。实际计算由节点 CPU 上的 SQLite
完成，另用独立 Python 逐项核对；不宣称 GPU 加速，也不代表真实客户结果。
原始数据留在节点，公开交付只保留方法与审查过的汇总，见
[实验说明与验证](../../experiments/lineage/README.md)。

这里最有价值的并非一张“连得很多”的图，而是点到任意结果时，都能分辨已有证据、
人工定义、未来意图以及仍然不知道的部分。
