# 智能数据基座：一手材料、核心判断与验收依据

核验日期：2026 年 10 月 25 日。用途是指导 SmartData 的设计与验收，不提供“已经成熟可用”的证明。网页和上游主分支持续变化，实际引入依赖仍需固定版本、核对许可证并通过本项目测试；仓库引用的固定版本见根目录 `research-lock.yaml`。

本文把内容分为三种：**已核验事实**是官方规范或项目自身文档明确说明的能力；**工程建议**是本项目据此作出的选择；**待验证假设**需要企业原始材料或运行实验支持。上游公开能力不等于本项目已完成适配，厂商自报收益也不等于 SmartData 的收益。

## 一、顶尖团队会先补齐哪些问题

首先会把愿景改写成可检查的承诺：服务谁、优先解决哪类问题、允许读取和修改什么、由谁确认业务含义、怎样判断任务已经完成。对“自动全面探测”还要加上覆盖分母；对“自动升级”要补充变更计划、影响范围、审批、恢复和验收条件。这些工作决定工程是否对准经营问题。

其次会划清四种权力：谁提供观察，谁决定业务规则，谁有权批准动作，谁判定实际结果。即使同一模型同时提出与复核建议，最终业务验收也应有独立观测或人工责任人。AI 风险管理不能只靠最后加一个审核按钮；NIST AI RMF 把治理、识别场景、测量与处置作为相互关联的工作。[NIST AI RMF 官方说明](https://airc.nist.gov/airmf-resources/airmf/)

还会先找难以伪装的失败：授权收回后还能否读到数据、分页是否漏单、旧快照是否被当成现况、两个客户的缓存是否串用、外部超时是否重复执行、指标变动是否能追溯到定义变化。这些检查常比继续增加模型角色更能提高可靠性。

产品方面会验证负责人是否看得懂范围、证据和限制；员工是否能补证、纠错、接管及找到任务结果。对美学的要求应落实为可用的视觉层次、克制色彩、稳定布局和有含义的动效，再辅以键盘、对比度和减少动画支持。WCAG 2.2 提供可测试的无障碍要求，但不能评价艺术品位，也不能保证全部用户需要都已满足。[WCAG 2.2](https://www.w3.org/TR/WCAG22/)

最后会设计退出路径：导出数据和工作记录、撤销凭据、删除索引、替换模型或连接器。普适基座的可扩展性应该由第二家、第三家企业的复用成本证明，不能仅由接口数量或架构图证明。

## 二、优先获取哪些原始材料，用什么方法

历史报告和 AI 回复适合帮助提出问题。确认真实企业需求，应优先使用下表材料，保留原始 ID、时间和采集范围。只收集任务所需的最小内容；密钥本身不能进入报告、日志或评测样例。

| 原始材料 | 能回答什么 | 具体方法与产物 |
|---|---|---|
| 正式 API/GraphQL 定义、授权 scope、分页与限流规则、脱敏原始响应 | 实际能读写什么，是否完整，授权怎样撤销 | 能力清单、契约测试、采集覆盖与失败报告 |
| 数据库 DDL、约束、索引、统计、脱敏样本、实际查询与执行计划 | 字段结构、唯一性、关联、质量与性能瓶颈 | 有上限的数据剖析、关系候选、查询计划分析；不把字段同名当成同义 |
| 任务调度配置、dbt manifest/run results、运行日志、血缘事件 | 数据从哪来、什么时候更新、改变会影响谁 | 还原来源链，比较声明依赖与实际运行；保留缺失链路 |
| 业务术语、计算口径、价格/退款/承诺政策、权限与审批记录 | “收入”“库存”“完成”的业务含义和责任 | 业务对象与指标契约；每项定义有负责人、版本与确认状态 |
| 订单、库存、支付、物流等实际事件及外部回执 | 真实状态变化，是否重复、晚到或互相冲突 | 跨系统对账、事件时间分析、身份匹配与不确定项登记 |
| 事故、客服/业务异常、人工修改、例外审批和恢复记录 | 经常失败在哪里，专家怎样纠错 | 按具体事件访谈，重建证据—决定—结果；写可执行验收条件 |
| 人工现状的处理时长、返工、损失、模型/云资源账单 | 效果和成本是否改善 | 建立基线、匹配对照、分层统计，记录未解决和接管任务 |
| 经授权的现场抽查、任务演示与业务人员复核 | 系统没有记录的情况、隐性规则 | 按决策需要补证；不默认采集全员屏幕、会议或行为 |

例如 Shopify 官方把读写能力分为具体访问范围，要求只申请产品需要的数据；部分资源另有额外批准条件。因此“有 API Key”不能替代“这次任务已获授权”。应在连接器中保存获准范围，并在执行时核对。[Shopify access scopes](https://shopify.dev/docs/api/usage/access-scopes)

业务建模建议采用事件梳理：围绕一次真实异常，按时间写清对象、状态变化、参与人、决定和证据；再让业务人员确认哪些环节必需、哪些是偶然做法。技术上用数据剖析、对账、血缘采集、契约测试和故障实验交叉验证。流程日志本身也不等于完整现实；OCEL 2.0 提供对象变化、对象间关系和事件关系的交换表示，可作为未来多对象流程导出格式。[OCEL 2.0 原始规范](https://arxiv.org/abs/2403.01975)

重要判定规则应由业务专家针对具体案例给出“什么条件满足才算对”，再由开发者写成独立校验。开放式分析采用明确的评分说明和人工抽查；交易结果优先读取源系统状态。模型评委的判断需要用人工样本校准。Anthropic 的原始工程文章将执行轨迹、实际结果和评分器分开讨论，适合参考，但其工程经验仍需在本项目任务上验证。[Demystifying evals for AI agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

## 三、最根本的需求框架

SmartData 的主干目标是：在企业授权内，建立可追溯的业务认识，组织人与助手共同处理问题，并能证明操作是否达成预期。

最小完整链是“接入 → 盘点 → 保留证据 → 诊断与补证 → 协作计划 → 获准执行 → 独立验证”。共享经验在结果验证后产生，不能反过来替代当前证据。任何阶段都应允许输出“还不知道”，并说明需要的观测和责任人。

目前应同时推进两条相连的工作：保住已有履约样板的审批、幂等与独立验证；补齐通用企业工作区、只读发现、体检、任务交接和可理解的前端。随后接真实数据和模型，再完成生产存储、权限、长流程及恢复能力。顺序和退出条件见[路线图](../roadmap.md)。

要避免三个混淆：资产目录描述“数据在哪里”，业务语义解释“它是什么意思”，业务执行规定“谁可以怎样改变它”。元数据平台、语义层、记忆库和智能体框架各自解决其中一部分，需要用共同身份、证据与权限契约连接起来。

## 四、经核验的上游能力，以及采用和排除理由

以下均为项目作者或规范维护方的一手页面。表中的“采用建议”是 SmartData 的设计判断，未表示对应适配已经落地。

| 一手来源与已核验事实 | 对 SmartData 的采用建议 | 明确边界 |
|---|---|---|
| [OpenMetadata 数据契约](https://docs.open-metadata.org/v1.12.x/api-reference/data-contracts)将结构、语义、质量与服务约定表达为可管理对象 | 复用目录、负责人、质量规则与契约结果；适配企业已有平台 | 契约声明与验证通过都不自动证明业务解释正确；不强制小企业安装整个平台 |
| [DataHub ingestion](https://docs.datahub.com/docs/metadata-ingestion/)支持按计划拉取元数据，也能通过 SDK 推送并进行变换 | 学习连接器能力声明、来源标识与增量更新；优先公开接口适配 | 不同时自建两套大型元数据目录；Core 与 Cloud 的能力和许可分别核对 |
| [OpenLineage](https://openlineage.io/docs/next/)围绕 dataset、job、run 及扩展元数据描述运行来源链 | 为数据处理作业采用可交换的血缘事件，减少逐厂商接线 | 只代表已经采集的加工链；不能据此推断未记录的依赖或授权 |
| [dbt MetricFlow](https://docs.getdbt.com/docs/build/about-metricflow?version=2)根据语义模型与指标定义生成 SQL | 对经营指标复用确认后的确定性计算；保存定义和版本 | 不把自然语言生成的任意 SQL 作为写工具；开放引擎与托管产品边界分别核对 |
| [Great Expectations Checkpoint](https://docs.greatexpectations.io/docs/core/trigger_actions_based_on_results/create_a_checkpoint_with_actions/)组织数据校验并根据结果触发后续动作 | 数据质量结果可以进入问题队列；候选规则先审核和回测 | 规则通过只覆盖规定维度，不代表数据全部真实；通知动作不等于业务修复获准 |
| [ODCS](https://bitol-io.github.io/open-data-contract-standard/latest/)定义结构、质量、责任、服务约定等可交换字段 | 数据契约保留导入/导出路径，降低客户锁定 | 标准文档优先于配套 Schema，仍需测试具体版本；不能代替本地权限执行 |
| [OPA](https://www.openpolicyagent.org/docs)将策略决定与业务执行分离，输入与输出可使用结构化数据 | 审批准入、模型路由和数据出口政策采用版本化规则 | 应用必须实际执行决定；策略不可用不能视作允许 |
| [OpenFGA](https://openfga.dev/docs/authorization-concepts)提供关系、角色、属性等授权建模概念 | 让员工、助手、企业和资产关系共同限制访问 | 关系许可不等于金额、证据时效和风险条件已满足；授权缓存需撤销传播 |
| [Temporal retry policies](https://docs.temporal.io/encyclopedia/retry-policies)明确工作流需可确定回放，API/模型等不确定操作放在 Activity 中 | 审批等待、超时、恢复与版本兼容沿用独立 Worker | 默认重试不是外部业务恰好一次；不确定写入先验证或人工对账 |
| [TencentDB-Agent-Memory](https://github.com/TencentCloud/TencentDB-Agent-Memory)描述分层记忆、异步提炼、混合查找和权限后检索 | 参考原始轨迹到可复用经验的分层与上下文预算 | 不把对话提取当业务事实，不直接引入其代理或授权实现；参考版本需锁定 |
| [ontology-driven-dev](https://github.com/sharptoolbox/ontology-driven-dev)以需求探索、本体建模、应用构建组织开发 | 学习先澄清业务对象与动作，再生成可检查契约 | 不复制示例运行时、安全边界或执行引擎；生成定义需人工确认 |

选型应由一次实际接入和一组异常测试决定。仓库星数、厂商引用量和功能清单适合发现候选，不构成安全、维护成本或业务准确性的证明。

## 五、什么外部标准能证明哪些结果

不存在一项通用标准能证明整套智能基座“对所有企业都正确”。外部标准提供明确的局部要求；业务正确性仍需真实状态、责任人和对照结果。下面是建议建立的要求—证据对应表，尚不表示项目已通过认证或全部检查。

| 标准或方法 | 它支持检查什么 | 本项目应交的证据 |
|---|---|---|
| [NIST AI RMF](https://www.nist.gov/itl/ai-risk-management-framework)及其 Govern/Map/Measure/Manage 四类工作 | AI 场景、责任、风险测量与处置是否成体系 | 每个用途的负责人、许可范围、失败后果、指标、人工接管和周期复核记录 |
| [OWASP ASVS 5.0.0](https://asvs.owasp.org/) | Web/API 身份、访问、输入、数据和通信等技术控制 | 用固定版本要求编号关联实现、测试和审计发现；未覆盖项明确列出 |
| [OWASP Agentic Top 10 2026](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/) | 智能体规划、工具使用、身份和协作引入的特有风险 | 提示注入、工具投毒、越权、记忆污染、跨助手信任和数据外传的攻击测试 |
| [WCAG 2.2](https://www.w3.org/TR/WCAG22/) | 视觉、键盘、焦点、输入与反馈的可访问性 | 自动扫描加键盘/读屏/缩放/减少动画人工检查，覆盖完整主要流程 |
| [Google SRE 的 SLO 方法](https://sre.google/workbook/implementing-slos/) | 可靠性是否按用户经历测量，是否有可接受错误范围 | 明确测量分母、窗口、延迟分位、失败率、告警、错误预算和恢复演练 |
| OpenAPI、JSON Schema、CloudEvents、OpenLineage 与 ODCS 的固定版本 | 系统能否按约定交换结构和事件 | 正反样例、兼容性、消费者契约、版本升级和导入导出测试 |
| 企业自己的业务政策、实际外部回执和专家验收 | 结果是否符合这家企业的业务要求 | 原始观察、批准条件、实际状态及通过/失败/无法判断的独立结果 |

NIST 的框架是自愿风险管理资源，官方页面显示 1.0 正在修订；落地时必须记录采用的具体版本。OWASP 风险清单适合指导攻击与防御范围，不能代替安全验证标准。SLO（服务可靠性目标）是承诺的测量阈值，错误预算是允许失败的份额；它们应围绕使用者能否完成工作制定。

## 六、验证与迭代怎样规模化

第一步，把每项需求写成独立可判定的条件。例如“发现订单快照过期，并给出原始时间和受影响任务”，比“诊断优秀”容易验证；“同一外部操作在超时和重复请求下不产生第二次副作用”，比“幂等测试通过”更接近业务要求。

第二步，按不同成本分层检查。规则、权限、状态机用快速单元与属性测试；接口使用消费者契约；数据库、消息、策略等用真实服务集成；完整路径用浏览器与 HTTP；故障、性能和恢复单独运行。不能用内存数据库的通过结果替代 PostgreSQL 的事务和行权限行为。

具体可采用的工具如下，均需在实施阶段固定兼容版本：

| 工具的一手依据 | 建议承担的工作 | 不能替代什么 |
|---|---|---|
| [Testcontainers](https://java.testcontainers.org/)提供测试期间可启动的真实依赖容器 | PostgreSQL、Kafka、策略服务等集成验证 | 生产拓扑的容量、备份与长期稳定性 |
| [Toxiproxy 模块](https://java.testcontainers.org/modules/toxiproxy/)支持网络故障实验 | 延迟、连接中断和恢复；结合服务端记录检查模糊超时 | 真实供应商的全部失败行为 |
| [Pact](https://docs.pact.io/)验证 HTTP 与消息消费双方约定 | 连接器、前端/API 和事件的兼容性 | 业务结果与实际权限正确性 |
| [k6 thresholds](https://grafana.com/docs/k6/latest/using-k6/thresholds/)将性能阈值变成测试通过条件 | 指定硬件、数据量和负载下的延迟/失败率验收 | 月度可用率或客户实际操作体验 |
| [Playwright 无障碍测试](https://playwright.dev/docs/accessibility-testing)支持结合 axe 检查常见问题 | 页面交互、视觉回归、键盘流程和自动扫描 | 人工可用性研究、读屏体验和全部无障碍问题 |

第三步，数据集分为公开学习集、开发回归集和独立隐藏验收集。案件不仅要覆盖正常路径，还要含身份歧义、晚到、过期、冲突、未记录事实、恶意文本、撤销授权与未知结果。每次评测冻结领域包、政策、模型、提示词、嵌入、工具、数据和评委版本。结果保存每类成功/失败、人工接管、成本和证据，不能只给总体平均分。

第四步，让每个连接器和领域包自带可复位样例、故障脚本和独立验证器。用固定随机种子生成更多变化，保留一组非开发者编写的真实案例检查生成器偏差；“生成了 500 个案件”不等于“有 500 种独立业务情况”。验证器的证据通道与智能体可修改区域分开，避免修改验收答案来取得成功。

第五步，进入真实企业时先建立人工基线，再只读、影子和审批执行。衡量处理时间与人工触点时，同时观察返工、逾期、投诉、错误干预和未解决比例。控制季节、活动和任务难度；样本不足或对照不充分时，应说“观察到相关改善”，不能宣称因果收益。

第六步，把新失败变成回归样例，按风险抽样复核共享经验和模型建议。可靠性下降或高风险错误触发退回上一阶段。扩展规模依靠连接器契约、领域验收包、自动测试分片和抽样审查，而不是让每个新客户从头做一次不可复用的咨询。

## 七、当前结论与尚需证明的假设

已得到一手资料支持的是：元数据与业务语义可以显式管理，数据契约和质量规则可以机器检查，来源链有开放交换格式，权限决定可以与执行分离，长流程可以保存与回放，智能体需要专门的结果评测。

本项目据此选择“轻量企业入口 + 可替换连接器/目录 + 共用证据与任务 + 受控执行内核”的路线。它能否降低部署和维护成本、三类助手是否比单助手或传统工作流更有效、自动生成的规则是否准确、审美重做是否提高理解与操作效率，均为待验证假设。应通过真实接入、对照任务和用户观察分别验证。

历史材料中的市场估值、AI 试点失败比例和厂商 ROI 不进入本项目的性能承诺。没有真实系统、真实权限和业务验收，本轮可以交付更完整的产品与工程路径，仍不能把软件原型称为成熟商用系统。
