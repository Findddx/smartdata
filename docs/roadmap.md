# SmartData 完整优化路线图

更新日期：2026 年 10 月 25 日。目标是企业可安装、可接入、可协作、可验证的智能数据基座。顺序依据依赖关系和风险安排，不用一个未经验证的日期承诺替代完成条件。项目背景和重要历史见[项目总纲](../PROJECT_CHARTER.md)。

## 首先把“成熟可应用”写成能验收的要求

以电商为第一条新增通用体验：负责人建立工作区，接入店铺、库存和分析数据，系统说明覆盖范围、定位问题、生成运维/分析/决策助手的协作计划，员工能补证、评论、认领、审批和核实结果。

任何“自动”能力都要说明三件事：已授权的范围、判断依据、结束条件。企业没有提供的接口、线下情况和指标定义，应进入待确认事项。“全面体检”必须附覆盖分母，例如已授权 8 个接口、成功检查 6 个、2 个因权限不足未检查；无法知道总量时明确报告覆盖未知。

产品完成度按以下门槛记录：

| 门槛 | 证明什么 | 不能据此宣称什么 |
|---|---|---|
| G0 本地体验 | 安装后能用公开样例跑通完整路径，重启保留工作区 | 已接好真实企业、已有真实收益 |
| G1 真实只读接入 | 客户系统的授权、增量读取、限流和撤销已验证 | 可以修改企业系统 |
| G2 业务影子运行 | AI 给建议，专家对照真实处理，记录差错与未知 | 已获准自主执行 |
| G3 审批执行 | 受限动作经批准，能防重复、对账、补偿并独立验证 | 所有业务都可以自动化 |
| G4 持续运营 | 可靠性、恢复、升级、安全和业务效果达到约定标准 | 一个行业的结果适用于全部行业 |

“影子运行”指系统跟随真实业务给建议，但不改变业务状态；目的是在不影响经营的情况下发现错误。“门槛”是一组必须通过的检查，而不是文档中的阶段名称。

## P0：让普通负责人完成第一轮企业体检

本轮已经交付可体验的本机接入、盘点、诊断与协作路径，并通过完整网络流程和重启恢复。
可选模型解释也通过真实本机 HTTP 桩验证。下表仍是完整产品要求，其中企业目标配置、
真实成员、敏感分类、业务口径与关系异常等尚未全部实现；具体已验证范围见
[阶段报告](reports/2026-10-25-workspace-delivery.md)。不能把“本地路径通过”当成 P0 全部要求达标。

| 工作 | 交付要求 | 验收方法 |
|---|---|---|
| 工作区和接入向导 | 企业目标、系统清单、成员/责任人、采集范围与本地保存 | 从空目录建立工作区，重启后记录仍在；演示与真实接入明确区分 |
| 可用的只读入口 | 标准 JSON 快照导入及受约束的 HTTP 读取；逐次显示采集状态、数据时间与错误 | 换一份新样例仍能发现资产；鉴权失败、超时、分页和无效数据不伪装成功 |
| 资产盘点 | 展示表/接口/字段、来源、负责人、更新情况、敏感分类和采集覆盖 | 与输入原件逐项对账；来源和未检查范围可见 |
| 数据体检 | 先做可解释的过期、缺失、重复、口径与关系异常检查；模型生成的诊断保留不确定性 | 注入已知问题，比较检出与误报；问题指向具体证据和规则版本 |
| 三类助手协作 | 运维、分析、决策任务有分工、负责人、依赖、评论、状态与成果 | 从一个发现的问题生成计划，人工补充/修改后推进到有证据的完成状态 |
| 工作台重做 | 清楚的导航与阅读层次；克制配色、质感、状态动画和上下文侧栏 | 桌面/窄屏、键盘、减少动画、错误/空/加载状态实际检查 |

JSON 是机器容易读取的结构化文本格式；快照是某次采集保存的数据副本；HTTP 是这里用于连接网络接口的通信协议。P0 的交付标准是“功能可独立体验，记录可以保存，结论能追到输入”。如果只读扫描仍由确定性规则完成、团队只是任务模板，界面与报告应直接说明。可选模型解释已走真实 SDK 验证，具体供应商、业务任务与自动调度仍有下一阶段的验收，不能以角色头像代替。

## P1：把真实企业接入做成可重复的产品能力

输入材料是正式 API 说明、最小权限账号、脱敏原始响应、分页与限流样例、业务对象 ID 规则和撤销方式。每个连接器都附“能力说明”：能读什么、需要什么权限、更新时间怎样解释、失败如何处理、是否能独立核实写入。

先完成一个真实电商系统与一个库存/订单来源，再验证第二种厂商是否复用同一框架。每个连接器都应覆盖认证失败、令牌撤销、重复/乱序事件、分页遗漏、字段变化、限流、断线续传及删除传播。账号或系统不可用时，保留上次观察时间，不能把陈旧快照显示为当前状态。

引入已有元数据平台时，优先选择 OpenMetadata 或 DataHub 中的一种适配路径，复用企业已经维护的目录、负责人、血缘和测试结果；“血缘”是某项数据经过哪些加工步骤得到的来源链。无此平台的小企业可以保留轻量内置目录，不强迫安装新平台。

P1 退出条件：两种异构来源成功接入；新企业无需改核心代码即可按说明完成配置；权限撤销后数据访问停止；能够提供源记录、资产清单和采集覆盖的对账报告。

## P2：让助手做真实、可核实的工作

模型通过已有的 `ModelPort` 等内部接口接入。Port 是替换具体厂商的接口，帮助在火山方舟、阿里百炼和客户私有模型之间切换，而不重写业务规则。配置中区分连接测试、获准发送的数据等级、预算和实际使用的模型版本。

三类助手各有限定任务和工具集。运维助手读取健康、采集与失败记录；分析助手使用经确认的指标和受限查询；决策助手组合已有证据与分析成果。它们通过任务和交接记录协作，任何工具调用都受当前用户与任务授权约束。

重要扩展：指标定义需有所有者、分子分母、时间范围、时区、币种、去重与退款规则；诊断结论须分“已观察事实、推测原因、待确认项”；分析结果须能用固定输入重新计算；建议须带成本、风险、可选方案与验收条件。

P2 退出条件：用冻结的真实脱敏案例对照人工答案；不同模型替换后权限与动作边界保持不变；推测不冒充事实；错误建议能被补证、退回和版本化修改。每个助手至少完成一类真实任务，并由相应业务责任人签收。

## P3：让已有执行内核成为可恢复的生产能力

这一阶段保留已经实现的安全语义，补齐实际基础设施：

| 缺口 | 为什么必须补 | 可检查的结果 |
|---|---|---|
| PostgreSQL 持久化与迁移 | 进程重启后案件、审批、凭证和任务不能丢失 | 事务、并发版本检查、租户隔离、升级/回退与恢复实测 |
| outbox/inbox 与消息适配 | 业务记录和待发事件不能各自成功一半 | 同一事务记录待发事件；重复消费不重复造成业务影响 |
| API 到 Temporal 编排 | 审批可能等几天，服务重启后仍应继续 | 工作进程崩溃、超时、旧版本流程回放都能验证 |
| OPA/OpenFGA | 外部权限与业务政策必须实际执行 | 关系权限、审批条件、数据出口规则；策略不可用时拒绝写入 |
| 客户侧连接器身份与签名授权 | 执行器需要验证请求确实来自获准流程 | 双向证书认证、授权有效期、单次使用、撤销和轮换测试 |
| 独立验证、对账和补偿 | 超时可能发生在实际成功之后 | 不盲目重试；未知结果可人工接管；补偿也要回读确认 |

outbox/inbox 是“待发送账本/已接收账本”，用于在数据库与消息系统之间防遗漏和去重；它不保证所有外部系统都恰好执行一次。Temporal 是保存长流程进度的工作流服务。OPA 根据结构化上下文判断规则，OpenFGA 判断人与对象之间的访问关系。两者给出决定后，业务服务仍需真正执行拒绝或放行。

P3 退出条件：在真实依赖容器和至少一个真实沙箱系统中，完成重复、乱序、提交前后崩溃、模糊超时、审批过期、权限撤销和断线恢复测试；所有写动作都有可追踪审批、回执和验证，越权与重复副作用为零。

## P4：让经验可以长期复用，让运营成本可控

将结案轨迹、经验候选、跨案件模式、经批准的处置手册分层保存。检索先检查权限和生命周期，再组合关键词与向量搜索；向量是便于查找语义相近内容的数值表示。检索输出附出处，摘要不覆盖原始记录。

经验撤销、源数据删除和权限变化需传递到索引、缓存和已排队任务。用定期对账检查撤销传播是否完成。保留“为什么不用过去经验”的解释，避免过期手册因相似度高而继续影响建议。

为每个工作区设采集频率、并发、模型用量与存储预算，显示单个经过验证任务的完整成本：模型、接入、人工复核、运维与返工。扩展连接器或助手前，先看维护成本和复用程度。

P4 退出条件：跨企业检索隔离、删除/撤销传播、索引重建和恢复均通过；共享记忆仅使用已批准且未过期的版本；新增企业和新模型不需要复制核心分支。

## P5：取得可供企业负责人判断的实用证据

进入真实试点前，取得 2–3 个真实系统、至少 500 个可追溯历史异常、业务负责人和专家审核人。500 是原计划的试点输入目标，不代表具有普遍统计证明力；样本还应覆盖罕见高风险失败、不同权限、跨时区、促销高峰与接口升级。

先记录人工现状，再只读、影子、审批执行。采用相似业务、相似时间与相似难度的对照；业务变化较大时需要单独分层，避免把促销或淡旺季的变化归功于 AI。公开效果报告应同时给出样本范围、时间、失败与人工接管情况，以及不确定性。

恢复和容量必须独立验收。原计划中的 50 活跃租户、500 并发用户、500 events/s 持续与 2,000 events/s 突发、千万级元数据、99.9% 可用性等保留为目标。先在公布的硬件和数据条件下压测，再持续观察；没有完整分母和测量窗口的延迟与可用率不作为达标证据。

P5 退出条件：业务指标经责任人签收；备份恢复、滚动升级、应急接管、证书/密钥轮换、数据删除和退出导出实际演练；安装与升级文档由未参与开发的人完成一次验证。

## 验证怎样随规模增长

每个领域包同时交付业务定义、连接器能力要求、异常样例和独立验收器。每次运行冻结数据、规则、领域包、模型、提示词和工具版本，生成可追溯的验收记录。这样扩展客户时复用的是一套可检查的交付包，不只是演示脚本。

测试按成本安排：代码变更跑快速规则与权限测试；合并前跑真实依赖集成与少量端到端路径；夜间跑大批异常和故障；发布前跑容量、安全与恢复；生产试点持续抽样复核和追踪延迟后果。新增失败先保留原始证据，再进入回归集；最终验收保留由独立负责人管理的隐藏集，开发过程不可反复查看答案。

外部依据包括 NIST AI RMF 的风险管理流程、OWASP 的应用与智能体安全要求、WCAG 2.2 的无障碍要求、SRE 的可靠性目标方法，以及 OpenLineage/ODCS 等数据交换规范。它们分别验证不同局部，不能合并成一张“AI 已正确”的证书。具体标准、工具及采用理由见[一手研究](research/2026-10-25-primary-sources.md)。

## 开源交付与项目管理

用户已同意新建开源仓库。发布内容应包含核心代码、公开接口、合成样例、安装指南、测试命令、许可证与版本化研究记录；个人原始材料、客户数据、密钥、缓存和本地运行数据不进入公开历史。发布后核对远端提交与本地版本，记录仓库地址和验证结果。

一项任务只有同时具备“负责人、用户可见成果、验收方法、证据位置、已知限制”才能关闭。每次跨阶段更新[项目总纲](../PROJECT_CHARTER.md)和实施状态；技术细节进入相应文档，总纲保留对使用者和决策有影响的信息。任何阶段发现错误都可以退回前一门，不能为了赶进度把未实现能力改写成已完成。
